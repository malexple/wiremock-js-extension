# Roadmap развития wiremock-js (v3 — актуализирован по итогам реализации 24.07.2026–28.07.2026)

Документ фиксирует анализ сильных сторон текущей реализации, план работ, принятые архитектурные решения и итоговый статус реализации по каждой фазе. Основа — сравнение с MockServer (JS/Velocity/Mustache templates) и модель governor limits Salesforce (Apex/Flow).

## Итоги анализа

### Подтверждённые преимущества (не трогаем, только усиливаем)

| # | Преимущество | Почему это важно |
|---|---|---|
| 1 | Безопасность из коробки (ScriptGuard: 100мс, лимит символов, 5 уровней вложенности) | MockServer/чистый JS позволяет `while(true)`, уронив контур; наш whitelist делает это архитектурно невозможным |
| 2 | Нет `undefined`/`null` крашей | `header()`/`query()` безопасно возвращают `null`, `contains()` работает с `null` без падения |
| 3 | Автоматическое приведение типов | `query("amount") > 1000` работает без `parseInt()`/`Number()` |
| 4 | Переиспользование через `scriptId` | Один скрипт — много маппингов, в MockServer код дублируется в каждом JSON |

## Принятые решения (24.07.2026, актуализировано 27–28.07.2026)

| Вопрос | Решение | Обоснование |
|---|---|---|
| Приоритет Фаза 1 vs Фаза 2 | Фаза 1 (JSON) первая | Show-stopper для 80% интеграционных тестов; Фаза 2 — вопрос эстетики, не принципиальной применимости |
| Глубина JSON-навигации в `jsonField()` | Изначально: точечная нотация + числовые индексы. **Фактически: полный Jayway JSONPath с фильтрами** (`items[?(@.status=='active')]`, `items[*].id`) | См. отдельную секцию "Решения, вышедшие за рамки первоначального плана" ниже |
| Область действия `jsonField()` | Только тело запроса (`body()` как JSON), а не произвольные объекты | Единственный реалистичный источник данных для навигации в контексте мока |
| `random()` и детерминизм | Опциональный `seed` в `ScriptDefinition`; если передан — `new Random(seed)`, если нет — `Math.random()`-эквивалент | Чистый рандом убивает воспроизводимость CI/CD; seed сохраняет детерминизм по требованию |
| Scope переменных | Function-scoped, плоская `Map<String, Object>` на весь вызов скрипта | Block-scoped (let/const) усложнит Visitor в разы; при лимите скрипта в единицы тысяч символов путаницы с var не будет — **подтверждено окончательно, пересмотру не подлежит** |
| Лимит длины скрипта | Вынести `MAX_SCRIPT_LENGTH` из хардкода в конфигурируемую переменную (system property, как `wiremockjs.storage.dir`) | Реализовано: `-Dwiremockjs.max.script.length`, по умолчанию 2000 |
| Интерполяция строк (template literals через `` ` ``) | **Не делаем — подтверждено окончательно** | Фаза 2 закрывает 70-80% боли через `var name = query("x"); "Hello " + name`; island grammar в ANTLR нерентабелен |
| Приоритет Фаза 3 vs Фаза 4 (по старой нумерации) | `random()` важнее полноценной интерполяции | Даёт новую бизнес-возможность (chaos engineering), а не косметику синтаксиса |
| **Доступ через точку к `var`-переменным** | **Разрешён** (`order.amount`, `order.details.city`), в отличие от изначального полного запрета | Компромисс: доступ к внутренним объектам WireMock (`request.*`) остаётся заблокирован, доступ к пользовательским данным становится удобным. См. секцию ниже |
| **Лимит на количество переменных (`MAX_VARIABLES`)** | **Не добавляем** — подтверждено окончательно | `MAX_SCRIPT_LENGTH` уже физически ограничивает число `var` (~220 при лимите 2000 символов); отдельный лимит не защищает ни от чего, но может случайно сработать при генерации большого JSON-ответа |
| **Защита `matches()` от ReDoS** | Используем движок **RE2J** вместо `java.util.regex` | RE2J — линейный DFA-автомат без backtracking, гарантирует `O(n)`; альтернатива (кастомный `CharSequence` с проверкой `Thread.interrupted()`) отклонена как менее надёжная |
| **`uuid()` и детерминизм** | `uuid()` генерируется на основе того же `Random`, что и `random()`/`randomInt()`, с ручной установкой version/variant битов по RFC 4122 | Обеспечивает воспроизводимость всей цепочки данных при фиксированном `seed`, включая идентификаторы — критично для компонентных/интеграционных тестов API |
| **`randomInt(min, max)` — границы** | Обе границы включительны (формула `max - min + 1`) | Избегает off-by-one ошибок, интуитивно понятно тестировщику; `min > max` бросает `ScriptExecutionException` |
| **Java-версия компиляции основного кода** | `compileJava { options.release = 11 }`, при этом toolchain и тесты — Java 21 | WireMock сам собран под Java 11 — совместимость по базовой версии обязательна для расширения |

## Решения, вышедшие за рамки первоначального плана

Два пункта из раздела "осознанно НЕ входит" были пересмотрены в процессе реализации и **больше не относятся к списку невключённого функционала** — ниже зафиксирована итоговая логика.

### 1. Доступ через точку к переменным (`var`)

**Было решено изначально:** произвольный доступ к полям через точку (`request.field`) — осознанно запрещено архитектурой, весь доступ только через whitelisted-функции.

**Реализовано фактически:** доступ через точку разрешён, но только для переменных, объявленных через `var` (`order.amount`, `order.details.city`, любая глубина вложенности). Доступ к внутренним объектам WireMock и любым необъявленным идентификаторам (`request.method`) остаётся заблокирован — если базовый идентификатор не найден в `scope`, интерпретатор бросает `ScriptExecutionException`.

**Почему это не нарушает исходный принцип:** защита от рефлексии по внутренним объектам WireMock сохранена полностью. Расширение касается исключительно данных, которые тестировщик сам явно ввёл в скрипт через `var` — то есть уже вычисленных, безопасных значений, а не прямого доступа к Java-объектам фреймворка.

**Технические гарантии реализации:**
- Многоуровневый обход через цикл по цепочке идентификаторов в `visitFieldAccessExpr`.
- Защита от `NullPointerException`: если промежуточное поле — `null`, дальнейшая навигация безопасно возвращает `null`.
- Строгая проверка типа: если базовое значение — примитив (строка, число), а скрипт пытается прочитать поле через точку, бросается `ScriptExecutionException` с понятным сообщением.

### 2. Полный Jayway JSONPath в `jsonField()`

**Было решено изначально:** точечная нотация + числовые индексы (`user.address.city`, `items.0.id`); полный JSONPath с фильтрами избыточен для whitelist-модели.

**Реализовано фактически:** `jsonField()` использует полноценный Jayway JSONPath, включая фильтры (`$.items[?(@.status=='active')].id`) и wildcard-выражения (`$.items[*].id`).

**Почему это принято как улучшение, а не риск:** это полностью компенсирует отсутствие циклов (`for`/`while`) в языке — фильтрация и агрегация по массивам теперь делается одной строкой JSONPath вместо ручной итерации, которую язык всё равно не смог бы предоставить безопасно.

**Обязательные меры защиты производительности (реализованы):**
- **Кэш скомпилированных путей** — `private static final Map<String, JsonPath> PATH_CACHE = new ConcurrentHashMap<>()` на уровне класса `RequestFacade`, общий для всех запросов. Исключает повторную компиляцию одного и того же JSONPath-выражения при каждом запросе.
- **Кэш распарсенного документа** — `DocumentContext` парсится максимум один раз за время жизни одного `RequestFacade` (то есть одного HTTP-запроса), лениво — только при первом реальном вызове `jsonField()`, не заранее. Повторные вызовы `jsonField()` в рамках одного скрипта (`jsonField("$.user.id")` и `jsonField("$.user.name")`) переиспользуют уже распарсенный документ.
- Флаг `documentContextInitialized` защищает от повторных попыток парсинга невалидного JSON-тела — при ошибке парсинга результат (`null`) кэшируется так же, как и успешный результат.
- Тест на 5000-элементном массиве с фильтром подтверждает отсутствие деградации производительности на реалистичном объёме данных (не покрывает теоретический worst-case с вложенными предикатами вида `@.a==@.b` — это осознанный компромисс, а не полное исключение риска).

## Финальный план реализации — фактически пройденные фазы

### Фаза 1 — JSON-доступ к телу запроса ✅

Функция `jsonField(path)` — полноценная JSONPath-навигация (Jayway) по телу запроса, с кэшированием путей и документа (см. выше). Работает только с телом текущего запроса — никаких произвольных внешних объектов.

```js
if (jsonField("$.user.role") == "admin") {
  return { "status": 200, "body": { "access": "granted" } };
} else {
  return { "status": 403, "body": { "access": "denied" } };
}
```

### Фаза 2 — Локальные переменные ✅

Грамматика: `varDeclaration`, `VarRefExpr`, плюс расширение `fieldAccess` для многоуровневой навигации по `var`-переменным. Плоский `Map<String, Object> scope` на уровне экземпляра `Visitor`, живёт ровно один вызов `execute()`.

```js
var token = header("Authorization");
var order = jsonField("$");
if (order.amount != null && contains(token, "secret") && order.amount > 1000) {
  return {
    "status": 400,
    "body": { "error": "Limit exceeded", "details": { "maxLimit": 1000, "currentAmount": order.amount } }
  };
}
return { "status": 200, "approved": true };
```

Побочные эффекты, также реализованные в рамках Фазы 2:
- `NULL`-литерал, null-безопасное `==`/`!=`.
- Настоящее короткое замыкание в `&&`/`||` (критичный баг найден и исправлен: изначальная реализация вычисляла оба операнда всегда, что ломало паттерн `x != null && x > 1000`).
- `MAX_SCRIPT_LENGTH` вынесен в system property `wiremockjs.max.script.length` (default 2000).
- Явные `ScriptExecutionException` вместо тихого приведения `null`/нечисловых значений к `0` в арифметике.

### Фаза 3 — random() с поддержкой seed ✅

Поле `seed` (Integer, опциональное) в `ScriptDefinition`. `Random` создаётся на уровне `WiremockJsInterpreter.execute(source, seed)`, передаётся в `Visitor`.

```js
if (random() < 0.05) {
  return { "status": 500, "body": { "error": "internal error" } };
} else {
  return { "status": 200, "body": { "ok": true } };
}
```

С `"seed": 42` в `ScriptDefinition` — воспроизводимая последовательность для CI/CD.

### Фаза 4а — Библиотека вспомогательных функций (первая волна) ✅

| Хелпер | Реализация | Особенность |
|---|---|---|
| `now()` | `Instant.now().toString()` | ISO-8601 с миллисекундами |
| `nowPlusDays(n)` | `Instant.now().plus(n, ChronoUnit.DAYS).toString()` | `n` может быть отрицательным |
| `uuid()` | Генерация из общего `Random` с ручной установкой битов версии/варианта (RFC 4122) | Детерминирован при заданном `seed` |
| `randomInt(min, max)` | `random.nextInt(max - min + 1) + min` | Обе границы включительны; `min > max` → `ScriptExecutionException` |
| `matches(str, pattern)` | `com.google.re2j.Pattern.matches()` | Защищено от ReDoS архитектурно (RE2J, линейный DFA) |

```js
var orderId = uuid();
var expiresAt = nowPlusDays(7);
return { "orderId": orderId, "expiresAt": expiresAt, "status": "created" };
```

## Что осознанно НЕ входит в этот roadmap

- Полноценные циклы (`for`/`while`) с governor-limits моделью по образцу Salesforce (счётчик итераций + таймаут) — отдельный будущий roadmap-пункт, требует собственного обсуждения безопасности. Без жёсткого контроля governor-limits циклы мгновенно «поломают» ScriptGuard; для 99% задач трансформации массивов хватает `jsonField()` с JSONPath-фильтрами.
- Template literals / интерполяция строк через бэктики — закрывается Фазой 2 через конкатенацию (`+`). Отказ экономит десятки часов на переписывании ANTLR-лексера под island grammar; конкатенация через `+` — база, понятная любому инженеру автоматизации.
- Block-scoped переменные (`let`/`const`) — не оправдано при лимите скрипта в единицы тысяч символов. Единственно верное решение при таком лимите: никто не пишет в моках модульный код, требующий сложной изоляции областей видимости внутри `if`-блоков.
- `csv`, `yaml`, `xpath`, `crypto` из Фазы 4 — без подтверждённого реального кейса от команды не добавляются. Защита от YAGNI: сохраняет плагин легковесным, быстрым и сфокусированным на REST/JSON. Если реально понадобится, например, подпись JWT «на лету» — это будет точечная доработка под конкретный запрос, а не заблаговременное раздувание whitelist и JAR.
- Лимит на количество переменных (`MAX_VARIABLES`) — не добавляется, `MAX_SCRIPT_LENGTH` уже достаточен физически.
